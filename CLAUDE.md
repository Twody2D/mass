# CLAUDE.md — Mass

Рабочие правила для Claude Code в этом репозитории. Полная конституция проекта — у владельца;
здесь её операционная выжимка. При конфликте побеждает конституция.

## Что это за проект

**Mass** — экспериментальная 3D-симуляция на Godot 4 для записи YouTube-видео.

> Цель: на одном обычном ПК одновременно симулировать и визуализировать до **10 000** простых
> персонажей на процедурном острове, сохраняя высокий FPS и позволяя управлять событиями мира
> в реальном времени.

Это **не** AAA-игра. Приоритеты по убыванию:
производительность → простота архитектуры → скорость разработки → надёжность →
расширяемость событий → зрелищность → красота графики.

## Жёсткие запреты

- ❌ **Никаких 10 000 нод.** Ни `CharacterBody3D`, ни `CollisionShape3D`, ни `NavigationAgent3D`,
  ни `AnimationPlayer`, ни отдельных `MeshInstance3D` на бота.
- ❌ **Никакого O(N²)** по ботам. Любая система, которая может стать O(N²), помечается явно
  и переделывается через spatial grid / hash / buckets.
- ❌ **Никакой полноценной физики и collision detection** между ботами без крайней нужды.
- ❌ **Dependabot запрещён.** Не создавать `.github/dependabot.yml`, workflow или конфиг.
  Предложения добавить его — игнорировать.
- ❌ Никакого CI/CD ради CI/CD.

## Внешние ресурсы

Внешние библиотеки, плагины и ассеты — модели, текстуры, шейдеры, addon'ы — **разрешены**,
если они действительно лучше: оптимизованнее, красивее и в стиле проекта. Раньше здесь стоял запрет;
владелец его снял.

Но выбор нужно обосновать: импорт должен **выигрывать** у своего решения по виду, цене или
скорости разработки, а не просто существовать. Остальные правила действуют без изменений:
никаких нод на бота, никакого O(N²), замеры на 100 → 1 000 → 5 000 → 10 000. Лицензия каждого
импорта фиксируется в `assets/CREDITS.md`.

## Архитектурные принципы

**Simulation и Rendering разделены.** Симуляция не знает про меши, рендер не лезет в логику.

Данные ботов — **Structure of Arrays** на `PackedFloat32Array` / `PackedByteArray`, а не массив
объектов. Причина: 10 000 GDScript-объектов = аллокации, refcount и медленный доступ по полям.

Рендер толпы — один `MultiMeshInstance3D`. Трансформы заливаются **одним присваиванием
`multimesh.buffer`**, а не 10 000 вызовами `set_instance_transform()`.

Тики разделены и не совпадают с кадром:

| Слой | Частота |
|---|---|
| Rendering | свободный FPS |
| Movement + upload буфера | фиксированный тик (сейчас 20 Гц) |
| AI decision | бакетами, 1/N ботов за тик |

Если система может работать реже без заметного визуального ухудшения — она **должна** работать реже.

Детерминизм: всё случайное идёт через seeded `RandomNumberGenerator`. Один `MAP_SEED` → одна карта
и один и тот же старт симуляции.

## Ответственности систем

| Система | Отвечает за | Не отвечает за |
|---|---|---|
| `GameConfig` | все настраиваемые константы | логику |
| `BotManager` | данные и поведение ботов | события, мир, рендер |
| `CrowdRenderer` | визуальное представление толпы | состояние ботов |
| `World` | карта, высоты, регионы | ботов |
| `EventManager` | мировые события | ботов напрямую |
| `Camera/Director` | камера | всё остальное |

События **не** зашиваются в `BotManager`. Их точка входа — `EventManager.trigger("meteor")`.

## Правила работы

1. Перед крупной функцией: изучи код → опиши затронутую архитектуру → короткий план →
   минимальная реализация → проверка → commit. Не по 10 функций за проход.
2. **Не угадывай.** Неочевидная архитектура — читай код. Несколько разумных вариантов, влияющих
   на архитектуру, — остановись и объясни варианты владельцу.
3. **Не ломай работающее.** Минимальные изменения, поиск зависимостей, проверка регрессий.
   Полный рефакторинг рабочей системы — только с объяснением зачем.
4. Начинай с минимальной реализации. 10 строк вместо 100. Godot API вместо новой библиотеки.
   Приблизительная симуляция вместо физически точной.
5. Не оптимизируй вслепую: измерь → найди bottleneck → измени → измерь снова.
6. Никаких тихих ошибок. Следи за null, невалидными индексами и bot id, отсутствующими нодами,
   плохими seed и параметрами событий.
7. Не делай задачи из `TODO.md` по своей инициативе. После выполнения — отметь и добавь новые
   найденные, но не превращай TODO в список хотелок.

## Производительность — это feature

При существенных изменениях проверяй FPS, CPU frame time, время симуляции, память, число render
instances и дорогих запросов. Обязательно на масштабах **100 → 1 000 → 5 000 → 10 000**.
Система не считается оптимизированной, если проверена только на 100 ботах.

## Секреты

В репозитории **не хранятся секреты**. Проект полностью локальный: нет бэкендов, ключей API
и учётных данных, и появляться они не должны.

Реальный риск в Godot ровно один: `export_presets.cfg` хранит пароль от Android keystore и ключ
шифрования скриптов **открытым текстом**. Он и все подписные материалы (`*.keystore`, `*.jks`,
`*.p12`, `*.pfx`, `*.pem`, `*.key`), а также `.env` и `override.cfg` — в `.gitignore`.

Если секрет когда-нибудь понадобится (например, ключ для загрузки билдов), он идёт в переменную
окружения или в игнорируемый файл, но не в трекаемые файлы. Репозиторий **публичный** — коммит
секрета означает мгновенную компрометацию, и удаление коммита её не отменяет: ключ нужно отзывать.

## Git

Conventional Commits, атомарные коммиты, каждый оставляет проект в рабочем состоянии.

```
<type>(<scope>): <description>
```

Типы: `feat` `fix` `perf` `refactor` `docs` `test` `chore`.
Scope: `simulation` `rendering` `world` `events` `camera` `ui` `core` `project`.

Хорошо: `feat(rendering): add multimesh crowd renderer`
Плохо: `update`, `changes`, `stuff`, `fix`, `feat: add bots, map, UI, events and camera`

**Никаких трейлеров авторства.** Сообщение коммита заканчивается телом. `Co-Authored-By: Claude`
и любые другие упоминания Claude в авторстве git **запрещены**: GitHub строит список Contributors
из авторов коммитов и `Co-authored-by:`, а Claude там быть не должен.

## Теги этапов

Проект снимается на видео, поэтому по нему нужно уметь ходить назад. Каждый `feat`-коммит,
дающий наблюдаемый результат, помечается аннотированным тегом:

```
stage-01-skeleton  stage-02-config  stage-03-island  stage-04-camera  stage-05-bots
```

Правила: тег ставится **только** на `feat`-коммит, дающий что-то видимое или измеримое;
`chore`, `docs` и `fix` не тегируются. Нумерация сквозная и не переиспользуется.

```
git tag -a stage-NN-name <hash> -m "Одна строка: что видно на этом этапе."
git push origin --tags
```

**Историю больше не переписываем.** Теги указывают на конкретные хеши, и любой `filter-branch`
или `rebase` по опубликованным коммитам их сломает.

## Definition of Done

Функция закончена, только если: работает; не ломает существующее; лежит в правильной системе;
нет очевидных ошибок; производительность проверена (если функция её затрагивает); документация
обновлена при необходимости; сделан Conventional Commit.

## После каждой задачи отчитывайся

1. Что сделано. 2. Какие файлы изменены. 3. Как работает. 4. Как проверено.
5. Performance-результат, если применимо. 6. Commit hash. 7. Следующий шаг.

Коротко. Главное — рабочий проект.

Пункт 22 (`Orbit`) добавил в риг второй реальный режим и первого настоящего потребителя
`CameraTarget`: центр либо у цели (живьём, каждый кадр), либо — если цели нет — точка впереди

одного элемента.

Пункт 23 (`FPV Drone`) — третий режим, теми же клавишами, что у `Free`, но с другой физикой отклика:
мягче инерция, крен в поворот, лёгкое покачивание в простое. Обзор демпфирован целиком (мышь
двигает цель, `_yaw`/`_pitch` её нагоняют), а крен читается прямо из разрыва между ними без
второго независимого сглаживания поверх — оно было в первой версии и давало обратный эффект: крен
ещё нарастал какое-то время после того, как мышь уже остановилась.

Пункт 24 (`Approach`) — четвёртый режим и первый непилотируемый: разово посчитанный подлёт к цели
по кривой Безье с разгоном и торможением через smoothstep, без единой клавиши
(`wants_mouse_capture() → false`). Путь считается один раз в `enter()` и дальше не меняется, даже
если цель движется, — меняется только то, куда камера смотрит, летя по уже готовой дорожке.
Долетев, зависает и продолжает смотреть на цель.

Пункт 25 (`Follow`) — пятый режим, тоже непилотируемый: встаёт позади цели и чуть выше, идёт следом
и разворачивается вместе с ней. В отличие от `Approach` пути тут нет вообще — «идеальная» точка
позади цели считается заново каждый кадр от текущей позиции и ориентации цели, а не от текущей
позиции камеры (первая версия так и делала и улетала в одну сторону бесконечно — самоссылающийся
оффсет). `CameraTarget` получил `resolve_facing()` — только для `BOT`, читает уже существующий
`BotManager.face_x`/`face_z`.

После `Follow`, по живому использованию, а не по тесту, нашлись и почищены два бага: крен
`FPV Drone` мог щёлкать между крайностями за один кадр при резком взмахе мышью влево-вправо (нужно
было вернуть сглаживание крену, но быстрое — заметно быстрее `LOOK_SMOOTHING`, а не медленнее, как
в баге до этого); и курсор мыши появлялся посреди кадра при переключении на `Approach`/`Follow` —
`CameraRig.capture_mouse()` теперь различает «режим не хочет мышь» (курсор скрыт) и «явный отпуск,
пауза» (курсор виден).

Пункт 26 (`Ground`) — шестой режим, тоже непилотируемый: штатив на высоте самого рыцаря в
нескольких метрах от цели, ради контраста масштаба с остальными режимами, которые смотрят на толпу
с сотен метров. В отличие от `Follow` не едет следом — врастает в землю один раз в `enter()` и
только поворачивается вслед за целью.

Пункт 27 (`Top`) — седьмой и последний перед `Director` режим, тоже непилотируемый: высоко над
целью, смотрит строго вниз, ориентация зафиксирована раз и навсегда (верх экрана — север, право —
восток) и никогда не довора­чивается ни к цели, ни сама по себе, в отличие от `Orbit`. Единственное
управление — колесо мыши, меняющее высоту; настоящую ортографическую проекцию не трогает
(`Camera3D.projection` — свойство рига, а не режима), «почти ортографический» вид даёт сама высота.
Отсюда — и только отсюда — читается форма ударной волны и то, куда течёт толпа.

Пункт 28 (`Director`) — не шестой режим, а диспетчер поверх пяти непилотируемых: каждый кадр
делегирует настоящему зарегистрированному на риге экземпляру `Orbit`/`Approach`/`Follow`/`Ground`/
`Top` (`CameraRig` получил `mode(id)` — найти режим по имени, не переключаясь на него; через
`set_mode()` `Director` работать не может, тот сам сменил бы «активного» посреди своего же кадра).
`Free`/`FPV Drone` не в ротации — пилотируемым нечего решать без игрока. Смена внутри `Director`
жёсткая, без блендинга рига — «режет», а не переходит, ровно как называет это сама формулировка
пункта. Простой таймер (6–14 с) берёт случайного живого бойца и случайный режим из четырёх; сигнал
`EventManager.shook` режет на `Top`/`Orbit` с целью на месте удара, с дебаунсом, чтобы одна тряска не
резала кадр дважды. `trigger()` сам не зовёт — когда падает метеорит, по-прежнему решает не камера.
Этим закрылась последняя дыра из «Открытых вопросов»: у `Orbit`/`Approach`/`Follow`/`Ground`/`Top`
наконец появилась настоящая, игровая цель — просто назначает её не игрок, а `Director`; вручную
навести один из этих пяти по-прежнему нечем.

Пункт 29 (раскалённая порода) — первый пункт среза 4, чисто визуальный: собственный шейдер камня
метеорита вместо `StandardMaterial3D`, освещение то же самое (`ALBEDO = COLOR.rgb`, та же раскраска
граней `BlobMesh`), поверх — направленное свечение по стороне, обращённой по направлению падения
(`local_heading`, пересчитывается каждый тик в текущее, вращающееся вместе с камнем локальное
пространство — камень крутится, мировое направление падения нет), и сеть трещин из трёх синусоидных
«плоскостей разлома» (тот же приём, что уже оправдал тряску камеры, — дёшево и похоже, не настоящий
шум), посчитанная от той же нормали, но **без** пересчёта в мировое направление — трещина обязана
крутиться вместе с камнем, а не плыть по кадру. Не проверено визуально: `--headless` не рендерит
фрагментный шейдер, `verify_events` ловит только то, что способен (материал строится и обновляется
без ошибок, цена тика не изменилась) — смотреть камерой на метеорит должен владелец.

Пункт 30 (слоёный хвост) заменил один конус, пытавшийся быть сразу всем, на четыре: пламя (тот же
конус, что был), ядро (второй, вложенный конус — не свой размер, а доля текущих длины/радиуса пламени,
поэтому растёт вместе с ним без отдельной синхронизации), дым (несколько блобов `smoke.gdshader`, всё
дальше друг за другом позади наконечника пламени, гаснущие с расстоянием — позиция и это доля
*текущей* длины пламени, а не фиксированное расстояние, иначе хвост растягивался бы, а дым оставался
прежней длины) и искры (разброшены внутри и вокруг пламени, а не позади — настоящие искры летят вбок
с рвущейся поверхности; мигают синусом на своей фазе от `_elapsed`, тем же приёмом, что уже оправдал
тряску камеры). Ничего не `GPUParticles3D` — тот же принцип, что уже держит `MushroomCloud`. Цена
несения метеорита выросла с 0.002 до 0.02 мс — на порядок, но по-прежнему один объект на всё видео, не
умножаемый на толпу. Тоже не проверено визуально, по той же причине, что и пункт 29.

Пункт 37 (LOD толпы) — первый пункт среза 5, сделан ровно по архитектуре, записанной в

переписывается при каждом пересчёте тиров, а не один раз при спавне: слот бота внутри буфера тира
сдвигается вместе с составом тира, даже если сам бот тир не менял. Новый `verify_crowd.gd`
проверяет границы дистанций, троттлинг пересчёта (тир не меняется на следующем кадре после
движения камеры, но обязательно меняется за `LOD_REFRESH_FRAMES` кадров) и что коарсер-тиры
реально дешевле по треугольникам. Не измерено: реальный FPS с LOD на 100 → 1 000 → 5 000 → 10 000
— headless этого не может, только владелец.

Пункт 38 (граф регионов и навигация) владелец сузил при постановке задачи: не полноценный
pathfinding с состоянием пути у каждого бота, как черновиком описывал `ARCHITECTURE.md`, а
перенаправление только уже существующих дальних отправок (`send_to()`/`gather_at()` — марш войны,
бегуны к сброшенному ящику), когда прямая линия туда режет открытую воду. Обычный wander не
тронут — он и так локальный (15–90 м) и уже проверяет `is_walkable()` на своей цели. `World`
строит грубую сетку регионов (`REGION_CELL_SIZE` = 64 м, ≈16×16 клеток) один раз при `generate()`
— один булев флаг «проходимо» на клетку, по высоте в её центре. Никакого хранимого пути у бота:
`World.route_waypoint(from, to)` считает всё заново на каждый вызов — сэмплирует прямую, и если
нигде не задело воду, отдаёт `to` без изменений (подавляющее большинство вызовов); если задело —
BFS по графу (250 узлов, дёшево искать с нуля) и в ответ уходит центр **второго** региона на пути,
ближайший шаг, а не весь маршрут. `WarBattle`'ый `REGROUP_SECONDS` (существовавший до этого пункта,
против отставших после стычки) оказался тем же самым механизмом, что нужен и перенаправлению:
застрявший на промежуточной точке боец получает свежий, чуть более продвинутый waypoint на
следующем перезыве сам по себе, без выделенного состояния «иду по пути». **Найдено не в реальном
ролике, а тестом (`verify_navigation.gd`), прежде чем что-либо ушло дальше**: первая версия BFS
отказывала в поиске, если центр-сэмпл самого стартового или целевого региона читался как вода, —
а прибрежный регион 64×64 м делает это сплошь и рядом, даже когда сама точка на суше внутри него
годится. Каждый дальний марш к настоящей прибрежной цели молча падал обратно на неизменённую
(заблокированную) точку. Починилось тем, что стартовый и целевой регион разрешены независимо от
своей проходимости — непроходимой обязана быть только клетка, через которую путь идёт транзитом.

**Тем же днём — закрыт последний открытый вопрос среза 6: оружие класса теперь влияет на бой, не
только на вид, по прямой команде владельца.** `resolve_combat()` уже считал для каждого защищающегося,

защищающегося (щит воина срезает урон независимо от того, кто бьёт). Направленную модель «чья дальность
считается, когда воин и лучник не согласны» — сознательно не строили: `melee_range` остаётся общей
геометрической дистанцией «достаточно близко для боя», не персональным оружием, это отдельная развилка,
которую никто не поднимал. Числа (`OFFENSE=[1.0, 1.3, 0.5]`, `DEFENSE=[0.65, 1.0, 1.35]`) подобраны так,

математику, сдвиг среднего далеко от 1.0 незаметно поменял бы, сколько тиков длится бой, без единого
проверяющего это теста. Воин читается как танк (худшая атака, лучшая защита), копейщик — как лучший
источник урона, лучник — слаб в обоих смыслах (лук не ближнее оружие, та же причина, по которой лучник

поднимал. Весь обязательный набор `verify_*` зелёный.

удалён): у раптора это длина (нос-хвост едва больше высоты и ширины), у скорпиона — ширина (размах

все трое добавлены в ростер `RandomBossEvent` (кнопка «случайный босс» теперь выбирает из девяти).
Весь обязательный набор `verify_*`, включая три новых теста, зелёный с первого прохода — ни одного
логического бага. **Но не чисто:** первый скриншот раптора и скорпиона (тем же
`tools/screenshot.tscn`, каким уже находили баг кратера-наклейки) прочитался как нечто
неопознаваемое — правильный урок из редизайна первого монстра («примитивы дают непонятные фигуры»)
здесь чуть не сработал наоборот. Причина — не модель, а ракурс: готовая рамка камеры в
`screenshot.gd` (фиксированное мировое смещение позади цели) случайно смотрела на раптора и
скорпиона почти в упор сбоку в момент снимка, а не на их «фасад». Изолированный превью-рендер (тот
же разовый инструмент, собран и удалён) с нескольких углов подтвердил: оба существа читаются ясно
анфас/на три четверти (лапы, когти, глаз, панцирь) — это не непонятные фигуры, а неудачный кадр.
Червя это не коснулось — его вытянутое тело читается одинаково с любого ракурса. Не выправлено
намеренно: чинить формулу рамки под конкретный ракурс для трёх боссов сразу — не тот масштаб
правки, который просили, и «дождаться реальной жалобы» — тот же принцип, что уже стоит в
«Открытых вопросах» про цвет сторон War. Подробности — ARCHITECTURE.md.

кнопки/клавиши боссов и добавить ещё боссов.** Первое: «мне не нужны отдельные кнопки для спавна
этих ботов, сделай по одной кнопке чтобы вызывался случайный» — девять клавиш
(`G`/`H`/`C`/`A`/`S`/`I`/`J`/`O`/`U`) и девять кнопок меню паузы убраны, остался только `B`/
«Случайный босс». Сами события никуда не делись — `EventManager` их по-прежнему регистрирует,
достать можно через `verify_*`, флаги `screenshot.gd` и ростер случайного босса; убраны только два

смерч, криперы и война не входят в `RandomBossEvent.ROSTER` вообще (это не «гигант, который дошёл,
получил урон и упал»).

Второе — третья тройка боссов, и первая, для которой урок предыдущей тройки применён заранее, а не
найден по факту: конь (`Horsely`), лев (`Rhombolion`), носорог (`Rombophant`) — специально выбраны
четвероногими, потому что тело вдоль оси движения читается силуэтом что анфас, что сбоку, что на
три четверти — в отличие от щита-лица скорпиона или гребня раптора. Шесть кандидатов прогнаны через
тот же разовый изолированный превью с трёх ракурсов, что в прошлый раз ловил проблему уже
постфактум — на этот раз он же её предотвратил: три нечитаемых (Peacolion, Firellama, Turtlelion)
отсеяны до единой строчки кода, три чистых пошли в дело. Твисты не про смещение точки атаки, как у
предыдущих: конь встаёт на дыбы при каждом реальном топтании (косметика, гаснет за
`REAR_KICK_SECONDS`, привязана не к таймеру обхода, а к тому, нашёлся ли кто-то реально под
ногами — иначе дыбился бы метрономом и по пустой земле), лев рычит по циклу, временно расширяя
радиус паники/бегства (`ROAR_RADIUS_MULT`), носорог целится не в одного бота, а в центр ближайшего
скопления вокруг случайного якоря — «заряд в гущу стада», а не погоня за одной целью. Оба
циклических твиста (конь, лев) потребовали от тестов гонять внутренние часы существа руками, а не
натуральными тиками — `SWEEP_SECONDS` (0.2 с) короче, чем окно затухания дыбов коня (0.3 с), значит
в настоящем бою конь никогда не успевает толком осесть до следующего топтания. Без отдельных
клавиш/кнопок — сразу в ростере `RandomBossEvent` (двенадцать). Все три подтверждены реальными
скриншотами в игре с первого раза, без единого неудачного ракурса — впервые в этой серии. Весь
обязательный набор `verify_*`, включая три новых теста, зелёный с первого прохода. Подробности —
ARCHITECTURE.md.

**2026-09-02: владелец накидал большой список правок разом** (баг вулкана, землетрясение

одноразовый `fire()` — рвёт новый разлом каждые 3.5 с на протяжении 30 с, без синглтон-гварда

меняющее heightmap **после** `generate()`: разлом теперь настоящая просадка рельефа (`get_height()`
читает из того же `_heights`), а не декаль поверх него, как `Crater`/старый `Fissure`. Полная стоимость

объяснена, не пофикшена: `is_walkable()` линейно сканирует растущий список разломов на каждой попытке
блуждающего бота выбрать точку, растёт с числом ударов землетрясения, не с числом ботов. Найденный
рассуждением, не падением теста баг: первая версия зажима глубины (`water_level + 1.0`) могла
**поднять** прибрежную клетку вместо того чтобы её опустить, потому что `SPAWN_MIN_HEIGHT` (0.6)
меньше — почищено до зажима `water_level + 0.1`. Volcano-баг («перекидывает на другой остров») по
чтению кода не воспроизведён — `verify_volcano` и загрузка сцены оба чистые; похоже на штатный переход
на отдельную карту вулкана, не краш, ждём подтверждения от владельца. Реальным скриншотом ещё не
проверено — сначала headless-рендер завис на этапе сохранения PNG по причине, не связанной с логикой
(разбирается отдельно), затем приоритет ушёл на землетрясение по выбору владельца. Подробности —
ARCHITECTURE.md, «Earthquake redesigned: continuous, and real pits».

**Следующим по списку — анимация оружия и стрелы, сделано.** Удар мечом/копьём — процедурная
анимация, не скелетная (ни у одной модели толпы нет костей отдельно от общего плоского
low-poly стиля `KnightMesh`, но у самого рыцаря, в отличие от боссов, костей и не было задумано —
это масштабируемая MultiMesh-геометрия). Найден и переиспользован по-настоящему свободный канал
custom data, который CLAUDE.md сам же документировал заранее (`INSTANCE_CUSTOM.z`, «зарезервирован
для variation, которую шейдер никогда не читал») — `CrowdRenderer` пишет туда флаг `State.FIGHTING`
каждый кадр, `knight.gdshader` тем же приёмом, что уже даёт качающиеся ноги при ходьбе (маска по
позиции вершины, не атрибут), поворачивает вершины меча/копья вокруг гарды/древка, пока флаг взведён
— бой уже даёт это состояние даром, ни `resolve_combat()`, ни `_sweep()` любого босса трогать не
пришлось. Стрелы лучников — новый `ArrowSwarm` (`scripts/rendering/arrow_swarm.gd`), пул из 32
слотов на одном `MultiMeshInstance3D`, тот же приём, что уже даёт `GroundEjecta` для обломков —
не нода на стрелу. Пока подключено только к `Monster` (пилот, тот же порядок, что и с анимацией
тела): каждый лучник в радиусе атаки с шансом 1-к-8 стреляет видимой стрелой в `_sweep()`, не
каждый — то же намеренное приближение, что уже даёт абстрактный урон-в-секунду вместо честного
подсчёта попаданий. К остальным боссам и к `resolve_combat()` (бой toлпа-на-толпу, `WarBattle`) не
подключено — сознательно, отдельное решение, не забытое: `resolve_combat()` бежит каждый тик по
потенциально тысячам лучников разом, и добавлять туда стрельбу — заметно более тяжёлая и рискованная
по производительности задача, чем то, что уже сделано для одного объекта-босса. Весь обязательный
набор `verify_*` зелёный, включая новую проверку в `verify_monster.gd` (стрелы реально вылетают:
12 выстрелов за один прогон боя). Реальным скриншотом не проверено — то же незавершённое
расследование зависания headless-рендера на этапе сохранения PNG, что и у Monster/Earthquake.

**Следующим по списку — смерч-рой, сделано.** Владелец: "не одно торнадо, а мировое испытание из
множества воронок, которые движутся сами по себе... сделать их более реалистичными". `TornadoEvent`
заменён на `TornadoSwarm` (`scripts/events/tornado_swarm.gd`) — тем же приёмом, что уже доказал
себя на `CreeperSwarm`: `fire()` зовёт `Tornado.start()` в цикле и усыновляет каждую воронку
отдельно, сам `Tornado` не знает, что он один из роя. Старый гвард «второе торнадо отклоняется»
снят — несколько воронок разом теперь и есть весь смысл; `id` остался `&"tornado"`, клавиша `T` и
кнопка меню не тронуты. «Реалистичнее» — двумя дешёвыми правками внутри `Tornado`, не физикой:
`size_mult` на воронку (0.7–1.35) масштабирует высоту/радиусы/дистанцию бегства напрямую, а силу
броска — через корень, так что рой выглядит семьёй разных воронок, а не клонами; и `_move()`
виляет вбок синусом на собственной случайной фазе вместо прямой линии к цели. «Убегают и
укрываются» не потребовало новой механики — `scare()` уже посылает бота прочь от точки, и с
несколькими воронками бот на пересечении их радиусов паники просто перескакивает, от какой
шарахнуться, тот же принцип «реагируй на ближайшую угрозу», на который уже опирается весь проект.
`verify_tornado.gd` переписан по образцу `verify_creepers.gd` (проверка точного числа воронок
вместо отклонённого повтора, плюс новая проверка, что после того как рой весь выдохся, остров
снова принимает свежий). Весь обязательный набор `verify_*` зелёный. Не проверено визуально — то
же незавершённое расследование зависания скриншота. Подробности — ARCHITECTURE.md, «Tornado
redesigned: a swarm, not one funnel».

**Дальше по очереди — пилот процедурного рига боссов, на `Crabylon`, сделано.** Владелец: "У
боссов нет анимаций... переставления ног... клешнёй берёт кого-нибудь... наступали, а не
прокатка". Ключевая находка: модели боссов на самом деле **рискованы** — `Skeleton3D` с
именованными FK-цепочками костей есть у всех проверенных (`Crabylon` — 44 кости, ноги и клешни;
`Horsely` — та же форма, ноги и хвост), просто без готового клипа `AnimationPlayer`. Ранний вывод
этой сессии "анимация в принципе невозможна" (сделан по проверке ТОЛЬКО отсутствия клипа) был
неполным — проверка боссов на скелет вообще не проводилась. Ось вращения для каждого сустава не
угадана, а измерена: разовый инспектор (`tools/inspect_model_tmp.gd`, построен-прогнан-удалён)
вывел настоящий `Skeleton3D.get_bone_global_rest()` каждой кости — у бедра ноги локальная Z почти
точно совпадает с мировой вертикалью, значит вращение вокруг неё качает ногу вперёд-назад в
горизонтальной плоскости (шаг, не взмах), у голени локальная X почти горизонтальна (сгиб
поднимает стопу), у плеча клешни та же вертикальная Z (разворот руки в сторону цели). Знак
(вперёд или назад) числа не показывают — честно записано как непроверенное. `Crabylon` теперь
идёт настоящим шаговым циклом (`Skeleton3D.set_bone_pose_rotation()`, шесть ног, две чередующиеся
триподы) и хватает клешнёй конкретного ближнего бойца, отдельно от площадного топота — сам топот
тоже переделан: раньше убивал всех в радиусе каждые 0.2 с непрерывно ("прокатка"), теперь раз в
реальный шаг (`STEP_PERIOD`). Найденный тестом (не рассуждением) баг: клешня сперва блокировалась
на ближайшей цели, которая почти всегда уже и в радиусе топота — топот убивал её первым, клешня
уходила в долгий кулдаун и не успевала повторить попытку. Починено исключением кандидатов внутри

резолвятся, `render()` реально уводит хотя бы одну кость от rest-позы — единственный тест в
проекте, что-либо проверяющий про кости) и отдельный счётчик `_grabbed` (не смешан со `_stomped`).
Остальные десять боссов не тронуты намеренно — владелец выбрал дублировать код по каждому файлу
босса, не общий класс, так что это доказательство техники на одном боссе, не готовая база для
остальных. Весь обязательный набор `verify_*` зелёный. Не проверено визуально — то же
незавершённое расследование зависания скриншота, и знак виляния особенно ждёт этой проверки.
Подробности — ARCHITECTURE.md, «Boss procedural rig pilot: Crabylon gets real bone animation».

**Дальше — первый звук в проекте, у крипера, сделано.** Владелец: "1-в-1 как в Minecraft... со
всеми анимациями и звуками". Через `AskUserQuestion` выбрал: полноценную звуковую систему (не
костыль только под крипера) и процедурную генерацию клипов — в проекте не было ни одного звукового
файла, лицензированных сэмплов ни у кого не спрошено, а искать их самостоятельно по интернету без
явной ссылки от владельца запрещено правилами инструментов. `ProceduralAudio`
(`scripts/audio/procedural_audio.gd`) синтезирует сырой 16-бит PCM в `AudioStreamWAV` с
кэшированием по параметрам (`noise_burst()`/`tone()` — общие примитивы для будущих событий,
`rising_whistle_hiss()`/`impact_boom()` — то, что понадобилось прямо сейчас), тот же приём
«построить один раз, переиспользовать», что уже даёт статический пул `BlobMesh`. `SoundEffect`
(`scripts/rendering/sound_effect.gd`) — обёртка под `adopt_visual()`, ровно контракт `GroundEjecta`
(`advance(delta) -> bool`, освобождает себя сама), таймер — по собственному `_elapsed` против
известной длительности клипа, не по `AudioStreamPlayer3D.playing` (это состояние реального
аудио-драйвера, никак не завязанное на `delta` симуляции, а headless вообще работает на
фиктивном драйвере без звука). `Creeper.start()` получил `on_fuse` — колбэк на момент поджога,
параллельно уже существующему `on_explode`; `CreeperSwarm.fire()` строит оба клипа один раз и
добавляет `events.adopt_visual(SoundEffect.create(...))` рядом с уже существующими визуальными
эффектами, сам `Creeper` по-прежнему ничего не знает про `EventManager`/звук. Реальный риск —
не крашится ли `AudioStreamPlayer3D` под headless-фиктивным драйвером — проверен эмпирически, не
предположен: `verify_creepers` прошёл чисто, включая замер на 10 000 (0.008 мс медиана / 4.54 мс
худший — не квадратично, чуть выше, чем до звука, за счёт узлов, не пересинтеза — клипы
кэшируются). Весь обязательный набор `verify_*` зелёный. Подключено пока только к криперу —
топот монстра, удар метеорита и другие боссы звука не получили, это отдельная, ещё не начатая
задача. Не проверено на слух — headless тоже не слышит. Подробности — ARCHITECTURE.md, «The
project's first sound: ProceduralAudio and the creeper's hiss/boom».

**Дальше — второй босс с процедурным ригом, конь (`Horsely`), сделано.** У коня уже было своё
вставание на дыбы при топоте (косметика поверх корневого `Node3D`) — не хватало настоящих ног под
галопом. Ось вращения измерена заново для ЭТОЙ модели тем же разовым инспектором, не
скопирована с краба — и оказалась противоположной: у краба локальная Z ноги совпадала с
вертикалью (нужно вращать вокруг вертикали, чтобы нога мела вбок — крабы ходят боком), у коня
локальная X всех ножных костей лежит строго в горизонтальной плоскости (нужно вращать вокруг
горизонтали, чтобы нога махала вперёд-назад по дуге — обычный галоп). Разные ответы — не потому
что риги сделаны по-разному, а потому что сама анимируемая походка разная; это и есть та часть
техники, которую стоило перепроверить на втором боссе, а не просто скопировать числа. Походка —
диагональная рысь (перед-право + зад-лево, затем наоборот), не тройка краба — у коня всего четыре
ноги, а не шесть, и это то, как настоящая лошадь на самом деле не путается в ногах на бегу.
Вставание на дыбы (вращает корневой узел) и новый шаговый цикл (вращает кости внутри скелета)

Первый пилот по звуку, которому пришлось добавлять инфраструктуру, а не переиспользовать — у Kraken
раньше вообще не было `_on_effect`, добавлен той же формы, что уже есть у Monster, через
`KrakenEvent.fire()`. Два разных примитива, не один и тот же: затягивание под воду — `noise_burst()`
без низкого баса (не `impact_boom()` — это исчезновение в воде, а не шаг по земле), привязано к
реальному захвату; погружение — настоящий глубокий `impact_boom()` (30 Гц/2 с), тот же приём «финал
звучит крупнее одного попадания», что уже у падения Monster. `verify_kraken.gd` получил ту же
проверку «хотя бы один живой звук после боя». Реализовано с первого прохода без единого найденного
бага. Весь обязательный набор `verify_*` зелёный. Не проверено на слух. Подробности —
ARCHITECTURE.md, «Sound, fourth pass: Kraken's own splash and sink».

**Владелец прервал прогон звука двумя багами с реального запуска: землетрясение должно бить быстрее,
и оно рвёт дыру в воде, а не только на суше — оба починены.** `_build_path()` вёл случайный обход из
пяти сегментов по 55 м вообще без проверки берега; `carve_rift()` при этом зажимает дно снизу
отметкой чуть выше уровня воды — если путь уходил в открытое море, эта зажимка не копала дно
глубже, а **поднимала** его почти до поверхности: настоящий гребень сквозь плоскую водную плоскость,
и есть та самая «дыра в воде». Чинить пришлось не саму зажимку (её уже правили раньше для другого,
похожего по симптому, но другого по причине случая — прибрежных клеток), а сам путь: он теперь
останавливается, как только следующий шаг оказался бы под водой. Заодно нашёлся и вырожденный
случай от этой же правки (путь из одной точки, если первый шаг сразу в воду) — `Fissure.create()`
на нём падал, починено проверкой длины перед вызовом. Интервал между ударами снижен с 3.5 до 2.0 с
(~15 ударов за 30 с вместо ~8-9) — прямая просьба по тому же прогону. `verify_earthquake.gd` получил
не более широкий прогон наудачу, а прямую проверку инварианта: отдельный зонд зовёт `_build_path()`
напрямую тридцать раз от точки у самого берега и проверяет, что каждая точка каждого пути — суша;
тест сразу поймал собственную ошибку в направлении пробной точки (`random_coast_point()` толкает в
море, не на сушу — выяснилось только при чтении кода), что подтвердило: тест действительно работает,
а не просто зелёный. Весь обязательный набор `verify_*` зелёный. Подробности — ARCHITECTURE.md,
«Earthquake: faster strikes, and a real bug the floor-clamp fix above did not actually close».

**Владелец в том же сообщении отметил вторую мелочь: клавиша `D` в `DebugHUD` всё ещё вызывает
`Drop`, хотя её просили убрать раньше.** Уточнено через `AskUserQuestion`, что именно убрать —
владелец выбрал убрать саму клавишу, не функцию `Drop` целиком: кнопка «Сброс груза» в меню паузы
и вся механика (`SupplyScramble`/`SupplyDropEvent`) не тронуты. Убран только `KEY_D`-кейс из
`_unhandled_input()` и упоминание `D drop` из `HINTS`. Весь обязательный набор `verify_*` зелёный.

**Тем же днём — владелец прогнал боссов на реальной сборке и нашёл настоящий, куда более крупный
баг, чем ожидалось.** Сообщения шли одно за другим со скриншотами: боссы заходят друг в друга,
лапки проходят сквозь тело, «слишком далеко машет ногами, дёрганый», краб «ходит боком либо
задом», курица «летает задом», червь «раскидывает в разные стороны», клешня краба доставала цель
у себя за спиной, и клавиша `W` всё ещё запускала войну (`A`/`S`/`D` уже заняты движением камеры,
`W` для войны не могла ужиться с `W` для «вперёд»). Расследование нашло не «знак направления»
(изначально заподозренный, задокументированный во всех 11 файлах как «не проверено визуально»), а
кое-что более фундаментальное: `Skeleton3D.set_bone_pose_rotation()` заменяет позу кости целиком,
а не добавляет поворот поверх её rest-ориентации — ни один ригованный босс ни разу не был
анимирован верно за всю серию. Отдельно — все 11 импортированных моделей физически смотрят в +Z,
не в -Z, которую предполагает `Basis.looking_at()` в каждом `_move()` (тот же баг независимо
нашёлся и в собственной геометрии `GiantBird`, построенной из примитивов, без импорта). Оба
найдены геометрическим замером (три одноразовых throwaway-инспектора, обычная практика этого
проекта — измерить, не гадать), не на глаз. Починено: `_local_rotation()` в каждом из 11 файлов
композирует rest-ориентацию с анимированным поворотом; тело развёрнуто на 180° в каждом `_build()`
(`GiantBird` — правкой знака Z у головы/клюва напрямую, у неё нет отдельного тела-узла); знак
качания ноги перепроверен для каждого рига после разворота (`Rhombolion`/`Rombophant`/`Monster`
действительно требовали правки, `Horsely`/`Giraffaxon`/`Raptorous` уже были верны, `Crabylon` дал
неопределённый сигнал и не тронут); амплитуда шага уменьшена вдвое во всех риг-боссах; гиганты
получили мягкое взаимное отталкивание (`push()` на каждом классе, `EventManager._separate_giants()`
раз в тик, `O(M²)` по числу гигантов — не толпе); клешня краба получила проверку направления;
клавиша `W` убрана из `DebugHUD` вместе со строкой в `HINTS`. Весь обязательный набор `verify_*`
зелёный. Подробности — ARCHITECTURE.md, «A real bug, much bigger than any leg's own sign».

**2026-09-02/03: следующий реальный прогон нашёл пять новых, независимых багов той же
природы.** Землетрясение: интервал между разломами сокращён втрое (2.0 → 0.67 с, ~45 ударов
за 30 с) по прямой просьбе владельца («в раза 3 быстрее»); отдельно почищен настоящий баг — кисть
карвинга (`reach`) шире самого разлома и у берега задевала настоящее морское дно, а зажим
`floor_height` **поднимал** его до уровня чуть выше воды вместо того чтобы оставить как есть,
получалась тонкая полка прямо на уровне воды — ровно то, что владелец описал как «под
землетрясением видно воду, а землетрясение над водой» (`Fissure` сэмплирует ту же высоту и
декаль повисала над этой полкой). Клетки, изначально лежащие под водой, кисть больше не трогает.
Rhombolion («ноги туда-сюда мотыляют»): у этой модели передняя нога (`Arm`/`ForeArm`, гуманоидный
риг) и задняя (`UpperLeg`/`Leg`) в одной диагонали измерились с противоположным знаком одной и
той же мировой оси — не то же самое, что зеркальные кости одного типа у Horsely/Rombophant/
Giraffaxon, у которых такого рассогласования нет. Один и тот же угол поворота отправлял переднюю
и заднюю ногу диагонали шагать в разные стороны одновременно; добавлен знак на ногу. Краб
(«ползёт боком и не смотрит куда идёт и кого есть»): тело краба намеренно развёрнуто
перпендикулярно ходьбе (настоящая крабья походка), но клешня проверяла «перед собой» по этому же
перпендикуляру, а не по направлению, куда краб реально идёт (`_pick_target`) — цель, к которой
краб буквально шёл, почти никогда не попадала в конус клешни. Клешня теперь целится по
направлению движения, отдельно от бортового «лица». Червь («мотыляет из стороны в сторону»): ось
волны хребта перепроверена тем же инспектором и осталась чисто горизонтальной без бокового
перекоса — вероятная причина в накоплении бокового сноса на цепочке из четырёх суставов с разной
фазой; амплитуда и сдвиг фазы уменьшены вдвое, та же мера, что уже помогала со «слишком
размашистым» шагом у других боссов. Весь обязательный набор `verify_*` зелёный, кроме одного
разового `FAIL` в `verify_zone` по перфомансу (247 мс против порога 200 — Zone в этой сессии не
трогался вовсе), подтверждённого прогревом машины: изолированный повторный запуск сразу дал
13.7 мс. Ни один из пяти багов не проверен визуально — реальным запуском владельца, headless этого
не может.

**2026-09-03: источник для новых боссов с готовой анимацией найден, первый пилот — дракон.**
Второй пакет из 10 кандидатов Polygonal Mind подтвердил: ни один не несёт `AnimationPlayer`, это
не невезение, а свойство всего набора. Через `AskUserQuestion` владелец выбрал искать другой
источник — найден Quaternius, "Ultimate Monsters" (CC0, подтверждено на первоисточнике). Владелец
выбрал дракона пилотом новой техники: проигрывание настоящего готового клипа
(`AnimationPlayer.speed_scale = 0` + ручной `seek()` из `render()`, тот же принцип «sim решает,
render только рисует», что уже держат все ручные риги) вместо ручного посева костей. `Dragon` —
первый воздушный гигант проекта: летает на фиксированной высоте над рельефом, никогда не касается
земли живым, падает и разбивается о землю при смерти синхронно с клипом `Death`. Зарегистрирован в
`EventManager` (`&"dragon"`) и `RandomBossEvent.ROSTER`, без отдельной кнопки/клавиши — как и все
боссы после того, как владелец собрал их в одну кнопку "случайный босс". Сделан с первого прохода
без единого найденного бага, новый `verify_dragon` зелёный сразу. Подробности — ARCHITECTURE.md,
«Dragon: baked animation clips, and the first aerial giant».

## Окружение

- Godot 4.7+ (Standard, не .NET), рендерер **Forward+**.
- Godot на машине разработчика может быть не установлен у Claude — запуск и замеры FPS
  выполняет владелец. Давай ему конкретные шаги проверки и ожидаемые цифры.
- Платформа: Windows. Shell — PowerShell (основной) и Git Bash.
- Godot в headless **не завершается**, если скрипт сцены не распарсился: процесс висит молча, без
  единой строки вывода. Инструменты запускать с `--quit-after 1200`, иначе диагностика съедает
  минуты на пустом месте.
