# CLAUDE.md — Mass

Рабочие правила для Claude Code в этом репозитории. Полная конституция проекта — у владельца;
здесь её операционная выжимка. При конфликте побеждает конституция.

## Что это за проект

**Mass** — экспериментальная 3D-симуляция на Godot 4 для записи YouTube-видео.

> Цель: на одном обычном ПК одновременно симулировать и визуализировать до **10 000** простых
> персонажей на процедурном острове, сохраняя высокий FPS и позволяя управлять событиями мира
> в реальном времени.

Это **не** AAA-игра. Приоритеты по убыванию:
производительность → простота архитектуры → скорость разработки → надёжность →
расширяемость событий → зрелищность → красота графики.

## Жёсткие запреты

- ❌ **Никаких 10 000 нод.** Ни `CharacterBody3D`, ни `CollisionShape3D`, ни `NavigationAgent3D`,
  ни `AnimationPlayer`, ни отдельных `MeshInstance3D` на бота.
- ❌ **Никакого O(N²)** по ботам. Любая система, которая может стать O(N²), помечается явно
  и переделывается через spatial grid / hash / buckets.
- ❌ **Никакой полноценной физики и collision detection** между ботами без крайней нужды.
- ❌ **Dependabot запрещён.** Не создавать `.github/dependabot.yml`, workflow или конфиг.
  Предложения добавить его — игнорировать.
- ❌ Никакого CI/CD ради CI/CD.

## Внешние ресурсы

Внешние библиотеки, плагины и ассеты — модели, текстуры, шейдеры, addon'ы — **разрешены**,
если они действительно лучше: оптимизованнее, красивее и в стиле проекта. Раньше здесь стоял запрет;
владелец его снял.

Но выбор нужно обосновать: импорт должен **выигрывать** у своего решения по виду, цене или
скорости разработки, а не просто существовать. Остальные правила действуют без изменений:
никаких нод на бота, никакого O(N²), замеры на 100 → 1 000 → 5 000 → 10 000. Лицензия каждого
импорта фиксируется в `assets/CREDITS.md`.

## Архитектурные принципы

**Simulation и Rendering разделены.** Симуляция не знает про меши, рендер не лезет в логику.

Данные ботов — **Structure of Arrays** на `PackedFloat32Array` / `PackedByteArray`, а не массив
объектов. Причина: 10 000 GDScript-объектов = аллокации, refcount и медленный доступ по полям.

Рендер толпы — один `MultiMeshInstance3D`. Трансформы заливаются **одним присваиванием
`multimesh.buffer`**, а не 10 000 вызовами `set_instance_transform()`.

Тики разделены и не совпадают с кадром:

| Слой | Частота |
|---|---|
| Rendering | свободный FPS |
| Movement + upload буфера | фиксированный тик (сейчас 20 Гц) |
| AI decision | бакетами, 1/N ботов за тик |

Если система может работать реже без заметного визуального ухудшения — она **должна** работать реже.

Детерминизм: всё случайное идёт через seeded `RandomNumberGenerator`. Один `MAP_SEED` → одна карта
и один и тот же старт симуляции.

## Ответственности систем

| Система | Отвечает за | Не отвечает за |
|---|---|---|
| `GameConfig` | все настраиваемые константы | логику |
| `BotManager` | данные и поведение ботов | события, мир, рендер |
| `CrowdRenderer` | визуальное представление толпы | состояние ботов |
| `World` | карта, высоты, регионы | ботов |
| `EventManager` | мировые события | ботов напрямую |
| `Camera/Director` | камера | всё остальное |

События **не** зашиваются в `BotManager`. Их точка входа — `EventManager.trigger("meteor")`.

## Правила работы

1. Перед крупной функцией: изучи код → опиши затронутую архитектуру → короткий план →
   минимальная реализация → проверка → commit. Не по 10 функций за проход.
2. **Не угадывай.** Неочевидная архитектура — читай код. Несколько разумных вариантов, влияющих
   на архитектуру, — остановись и объясни варианты владельцу.
3. **Не ломай работающее.** Минимальные изменения, поиск зависимостей, проверка регрессий.
   Полный рефакторинг рабочей системы — только с объяснением зачем.
4. Начинай с минимальной реализации. 10 строк вместо 100. Godot API вместо новой библиотеки.
   Приблизительная симуляция вместо физически точной.
5. Не оптимизируй вслепую: измерь → найди bottleneck → измени → измерь снова.
6. Никаких тихих ошибок. Следи за null, невалидными индексами и bot id, отсутствующими нодами,
   плохими seed и параметрами событий.
7. Не делай задачи из `TODO.md` по своей инициативе. После выполнения — отметь и добавь новые
   найденные, но не превращай TODO в список хотелок.

## Производительность — это feature

При существенных изменениях проверяй FPS, CPU frame time, время симуляции, память, число render
instances и дорогих запросов. Обязательно на масштабах **100 → 1 000 → 5 000 → 10 000**.
Система не считается оптимизированной, если проверена только на 100 ботах.

## Секреты

В репозитории **не хранятся секреты**. Проект полностью локальный: нет бэкендов, ключей API
и учётных данных, и появляться они не должны.

Реальный риск в Godot ровно один: `export_presets.cfg` хранит пароль от Android keystore и ключ
шифрования скриптов **открытым текстом**. Он и все подписные материалы (`*.keystore`, `*.jks`,
`*.p12`, `*.pfx`, `*.pem`, `*.key`), а также `.env` и `override.cfg` — в `.gitignore`.

Если секрет когда-нибудь понадобится (например, ключ для загрузки билдов), он идёт в переменную
окружения или в игнорируемый файл, но не в трекаемые файлы. Репозиторий **публичный** — коммит
секрета означает мгновенную компрометацию, и удаление коммита её не отменяет: ключ нужно отзывать.

## Git

Conventional Commits, атомарные коммиты, каждый оставляет проект в рабочем состоянии.

```
<type>(<scope>): <description>
```

Типы: `feat` `fix` `perf` `refactor` `docs` `test` `chore`.
Scope: `simulation` `rendering` `world` `events` `camera` `ui` `core` `project`.

Хорошо: `feat(rendering): add multimesh crowd renderer`
Плохо: `update`, `changes`, `stuff`, `fix`, `feat: add bots, map, UI, events and camera`

**Никаких трейлеров авторства.** Сообщение коммита заканчивается телом. `Co-Authored-By: Claude`
и любые другие упоминания Claude в авторстве git **запрещены**: GitHub строит список Contributors
из авторов коммитов и `Co-authored-by:`, а Claude там быть не должен.

## Теги этапов

Проект снимается на видео, поэтому по нему нужно уметь ходить назад. Каждый `feat`-коммит,
дающий наблюдаемый результат, помечается аннотированным тегом:

```
stage-01-skeleton  stage-02-config  stage-03-island  stage-04-camera  stage-05-bots
```

Правила: тег ставится **только** на `feat`-коммит, дающий что-то видимое или измеримое;
`chore`, `docs` и `fix` не тегируются. Нумерация сквозная и не переиспользуется.

```
git tag -a stage-NN-name <hash> -m "Одна строка: что видно на этом этапе."
git push origin --tags
```

**Историю больше не переписываем.** Теги указывают на конкретные хеши, и любой `filter-branch`
или `rebase` по опубликованным коммитам их сломает.

## Definition of Done

Функция закончена, только если: работает; не ломает существующее; лежит в правильной системе;
нет очевидных ошибок; производительность проверена (если функция её затрагивает); документация
обновлена при необходимости; сделан Conventional Commit.

## После каждой задачи отчитывайся

1. Что сделано. 2. Какие файлы изменены. 3. Как работает. 4. Как проверено.
5. Performance-результат, если применимо. 6. Commit hash. 7. Следующий шаг.

Коротко. Главное — рабочий проект.

## Текущий этап

**Срез 4 идёт, следующий пункт 32 (метеорит v2: подсветка сцены на подлёте).** Полный план проекта —
42 пункта плюс раздел «Баги» в `TODO.md`, порядок значим. Срез 4 — визуальная доводка уже
существующего метеорита, `feat(events)`; владелец явно скомандовал войти в него после того, как
срез 3 (камера) был закрыт полностью, и затем — продолжать без остановки между пунктами.

Пункты 1–31 и 43 закрыты: остров, толпа, движение, столкновения, камера, меню, debug-панель,
смерть, `EventManager`, метеорит, реакция толпы на удар, потоп, сжимающаяся зона, война команд,
сброс грузов, замеры всех событий разом, `CameraRig` с перенесённым в него `Free`, `Orbit`,
`FPV Drone`, `Approach`, `Follow`, `Ground`, `Top`, `Director`, раскалённая порода метеорита, слоёный
хвост и отделяющиеся обломки. Измерено на 10 000 рыцарей на Intel UHD Graphics:
тик 16.4 мс (32.9% бюджета 20 Гц), удар метеорита 15 мс, прилив 0.5 мс, обход зоны 0.07 мс,
разрешение боя 20.1 мс медиана (2000 против 2000), обход сброса груза 0.02 мс медиана (четыре
ящика разом). Полный тик + событие вместе (`profile_events --total`) на 10 000 у всех пяти событий
укладывается в 27–45% бюджета по медиане (13–22 мс), худшие одиночные тики — 66–98% (33–49 мс); ни
один рост от 100 к 10 000 не квадратичен. Ничего не чинилось по итогам — числа ровные, чинить было
нечего.

Пункты 20 и 21 сделаны одним коммитом по решению владельца: рига без единого реального режима
нечем было проверить и не на чем показать блендинг, поэтому `CameraRig` сразу строился с `Free`,
перенесённым в него как `FreeCameraMode`, а не как пустая оболочка.

Пункт 22 (`Orbit`) добавил в риг второй реальный режим и первого настоящего потребителя
`CameraTarget`: центр либо у цели (живьём, каждый кадр), либо — если цели нет — точка впереди
камеры на момент переключения. `Tab` теперь реально что-то переключает, а не крутит реестр из
одного элемента.

Пункт 23 (`FPV Drone`) — третий режим, теми же клавишами, что у `Free`, но с другой физикой отклика:
мягче инерция, крен в поворот, лёгкое покачивание в простое. Обзор демпфирован целиком (мышь
двигает цель, `_yaw`/`_pitch` её нагоняют), а крен читается прямо из разрыва между ними без
второго независимого сглаживания поверх — оно было в первой версии и давало обратный эффект: крен
ещё нарастал какое-то время после того, как мышь уже остановилась.

Пункт 24 (`Approach`) — четвёртый режим и первый непилотируемый: разово посчитанный подлёт к цели
по кривой Безье с разгоном и торможением через smoothstep, без единой клавиши
(`wants_mouse_capture() → false`). Путь считается один раз в `enter()` и дальше не меняется, даже
если цель движется, — меняется только то, куда камера смотрит, летя по уже готовой дорожке.
Долетев, зависает и продолжает смотреть на цель.

Пункт 25 (`Follow`) — пятый режим, тоже непилотируемый: встаёт позади цели и чуть выше, идёт следом
и разворачивается вместе с ней. В отличие от `Approach` пути тут нет вообще — «идеальная» точка
позади цели считается заново каждый кадр от текущей позиции и ориентации цели, а не от текущей
позиции камеры (первая версия так и делала и улетала в одну сторону бесконечно — самоссылающийся
оффсет). `CameraTarget` получил `resolve_facing()` — только для `BOT`, читает уже существующий
`BotManager.face_x`/`face_z`.

После `Follow`, по живому использованию, а не по тесту, нашлись и почищены два бага: крен
`FPV Drone` мог щёлкать между крайностями за один кадр при резком взмахе мышью влево-вправо (нужно
было вернуть сглаживание крену, но быстрое — заметно быстрее `LOOK_SMOOTHING`, а не медленнее, как
в баге до этого); и курсор мыши появлялся посреди кадра при переключении на `Approach`/`Follow` —
`CameraRig.capture_mouse()` теперь различает «режим не хочет мышь» (курсор скрыт) и «явный отпуск,
пауза» (курсор виден).

Пункт 26 (`Ground`) — шестой режим, тоже непилотируемый: штатив на высоте самого рыцаря в
нескольких метрах от цели, ради контраста масштаба с остальными режимами, которые смотрят на толпу
с сотен метров. В отличие от `Follow` не едет следом — врастает в землю один раз в `enter()` и
только поворачивается вслед за целью.

Пункт 27 (`Top`) — седьмой и последний перед `Director` режим, тоже непилотируемый: высоко над
целью, смотрит строго вниз, ориентация зафиксирована раз и навсегда (верх экрана — север, право —
восток) и никогда не довора­чивается ни к цели, ни сама по себе, в отличие от `Orbit`. Единственное
управление — колесо мыши, меняющее высоту; настоящую ортографическую проекцию не трогает
(`Camera3D.projection` — свойство рига, а не режима), «почти ортографический» вид даёт сама высота.
Отсюда — и только отсюда — читается форма ударной волны и то, куда течёт толпа.

Пункт 28 (`Director`) — не шестой режим, а диспетчер поверх пяти непилотируемых: каждый кадр
делегирует настоящему зарегистрированному на риге экземпляру `Orbit`/`Approach`/`Follow`/`Ground`/
`Top` (`CameraRig` получил `mode(id)` — найти режим по имени, не переключаясь на него; через
`set_mode()` `Director` работать не может, тот сам сменил бы «активного» посреди своего же кадра).
`Free`/`FPV Drone` не в ротации — пилотируемым нечего решать без игрока. Смена внутри `Director`
жёсткая, без блендинга рига — «режет», а не переходит, ровно как называет это сама формулировка
пункта. Простой таймер (6–14 с) берёт случайного живого бойца и случайный режим из четырёх; сигнал
`EventManager.shook` режет на `Top`/`Orbit` с целью на месте удара, с дебаунсом, чтобы одна тряска не
резала кадр дважды. `trigger()` сам не зовёт — когда падает метеорит, по-прежнему решает не камера.
Этим закрылась последняя дыра из «Открытых вопросов»: у `Orbit`/`Approach`/`Follow`/`Ground`/`Top`
наконец появилась настоящая, игровая цель — просто назначает её не игрок, а `Director`; вручную
навести один из этих пяти по-прежнему нечем.

Пункт 29 (раскалённая порода) — первый пункт среза 4, чисто визуальный: собственный шейдер камня
метеорита вместо `StandardMaterial3D`, освещение то же самое (`ALBEDO = COLOR.rgb`, та же раскраска
граней `BlobMesh`), поверх — направленное свечение по стороне, обращённой по направлению падения
(`local_heading`, пересчитывается каждый тик в текущее, вращающееся вместе с камнем локальное
пространство — камень крутится, мировое направление падения нет), и сеть трещин из трёх синусоидных
«плоскостей разлома» (тот же приём, что уже оправдал тряску камеры, — дёшево и похоже, не настоящий
шум), посчитанная от той же нормали, но **без** пересчёта в мировое направление — трещина обязана
крутиться вместе с камнем, а не плыть по кадру. Не проверено визуально: `--headless` не рендерит
фрагментный шейдер, `verify_events` ловит только то, что способен (материал строится и обновляется
без ошибок, цена тика не изменилась) — смотреть камерой на метеорит должен владелец.

Пункт 30 (слоёный хвост) заменил один конус, пытавшийся быть сразу всем, на четыре: пламя (тот же
конус, что был), ядро (второй, вложенный конус — не свой размер, а доля текущих длины/радиуса пламени,
поэтому растёт вместе с ним без отдельной синхронизации), дым (несколько блобов `smoke.gdshader`, всё
дальше друг за другом позади наконечника пламени, гаснущие с расстоянием — позиция и это доля
*текущей* длины пламени, а не фиксированное расстояние, иначе хвост растягивался бы, а дым оставался
прежней длины) и искры (разброшены внутри и вокруг пламени, а не позади — настоящие искры летят вбок
с рвущейся поверхности; мигают синусом на своей фазе от `_elapsed`, тем же приёмом, что уже оправдал
тряску камеры). Ничего не `GPUParticles3D` — тот же принцип, что уже держит `MushroomCloud`. Цена
несения метеорита выросла с 0.002 до 0.02 мс — на порядок, но по-прежнему один объект на всё видео, не
умножаемый на толпу. Тоже не проверено визуально, по той же причине, что и пункт 29.

Пункт 31 (отделяющиеся обломки) — единственное место во всём файле, где вообще понадобился `World`:
оторвавшийся кусок падает своей баллистикой (`BotManager.GRAVITY`, та же, что у брошенного метеоритом
рыцаря) и обязан знать, где земля, чтобы остановиться, а не провалиться. Передан как `Callable`
(`world.get_height`), не ссылка на `World`, — тот же приём, что уже был у `ShockwaveEffect`. Куски
рисуются одним `MultiMeshInstance3D` (владелец явно потребовал именно это, не узел на кусок) — та же
логика, что у `CrowdRenderer`, просто на масштабе, где она не была бы обязательна. Позиция каждого
куска — мировая, не локальная (после отделения он летит отдельно от продолжающего падать метеорита);
в трансформ инстанса переводится через `to_local()` каждый тик, дёшево, поскольку сам корпус (не
вращающийся `_rock` внутри него) ориентацию не меняет за весь полёт. Ещё не отделившийся кусок скрыт
нулевым масштабом — у `MultiMesh` нет per-instance visibility. Цена несения метеорита — 0.02 → 0.04
мс, снова на месте. Тоже не проверено визуально.

**Замеры на этой машине.** Мерить медианой, один размер толпы на процесс
(`profile_tick --count=10000`) и всегда в холодном процессе: чистый арифметический цикл показывает
66 мс в начале и 219 мс после трёхсот кадров. Проверки `verify_*` бюджет **не сторожат** — их
границы ловят только алгоритм, ушедший в квадрат.

`DEFAULT_BOT_COUNT` временно стоит на 1000 — рабочее значение на время разработки. Целевое
значение проекта остаётся 10000.

**Стоп.** Оружие, экономику, города, новые события и любые новые механики не добавлять без явной
команды владельца. Следующие задачи — в `TODO.md`, и брать их по своей инициативе нельзя.

Перед прогоном проверок после добавления нового `class_name`: Godot не увидит класс, пока проект
не пересканирован — `--headless --editor --quit-after 400` один раз.

## Окружение

- Godot 4.7+ (Standard, не .NET), рендерер **Forward+**.
- Godot на машине разработчика может быть не установлен у Claude — запуск и замеры FPS
  выполняет владелец. Давай ему конкретные шаги проверки и ожидаемые цифры.
- Платформа: Windows. Shell — PowerShell (основной) и Git Bash.
- Godot в headless **не завершается**, если скрипт сцены не распарсился: процесс висит молча, без
  единой строки вывода. Инструменты запускать с `--quit-after 1200`, иначе диагностика съедает
  минуты на пустом месте.
- Каждая система прикрыта сценой-проверкой в `tools/`. Перед коммитом прогонять все: `verify_world`,
  `verify_camera`, `verify_camera_rig`, `verify_orbit`, `verify_fpv_drone`, `verify_approach`,
  `verify_follow`, `verify_ground`, `verify_top`, `verify_director`, `verify_bots`, `verify_movement`,
  `verify_hud`, `verify_menu`, `verify_death`, `verify_events`, `verify_reaction`, `verify_flood`,
  `verify_zone`, `verify_war`, `verify_drop`.
